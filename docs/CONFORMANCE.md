## 7. Prioritized gap list

Ordered by what actually stands between this build and the launch gate, *"the first session reliably reaches 'I locked an app and started.'"* (§1.5), separating genuine blockers from things that only need a Mac or an API key.

### State this plainly before anything else

**"Locked" today means a self-honesty commitment device, not a technical restriction.** `core/blocking/SoftBlockingStrategy.ts:1-18` documents this about itself: `applyShield` "does NOT block apps at the OS level," it only flips an in-app state flag the UI subscribes to. `core/blocking/index.ts:40-53` (`getBlockingStrategy`) confirms every shared branch of this repo always returns that soft strategy, `FEATURE_FLAGS.IGNITION_NATIVE` is false everywhere except a real Mac build with the Family Controls entitlement granted, neither of which exists in this repo's reach. Nothing stops the OS from switching to a "locked" app today. This is explicitly the PRD's own planned launch path (its risk table says exactly this: ship the soft lock, never gate launch on the entitlement), so it is not a code defect, but it must not be described as more than it is in a demo, an App Store listing, or anywhere else. The timer, the banner, and the panic-valve friction are real. The OS-level block is not, yet.

### Top 5 genuine blockers/risks (not solved by a Mac or a key)

1. **FR-44's promised "single user-set strength control" does not exist anywhere in the UI.** `components/stakes/StakeSetupSheet.tsx:602-604` deliberately renders stake strength as a read-only `Badge`, its own comment says "words, not a slider the user must reason about." The only writer of `stakeStrength` besides the fixed default is one-way, automatic de-escalation (`store/stakesStore.ts:995`). This is the sharpest finding of this round because it directly contradicts both FR-44's text and `09_Decisions.md`'s "fixed defaults plus one user control," and it was graded DONE last audit on the strength of the wrong evidence (a writer existed, but not a user-facing one). Needs a decision: build the control, or update the two docs that promise it.
2. **FR-65's Settings screen has real, findable content bugs, not just missing controls.** `components/settings/StakesSettings.tsx:320-330`'s "Longest single lock" row displays the daily cap value under a label that should show the single-session cap, `Settings.singleSessionCapMin` is never read in that file at all. A user checking "what's the longest one session can lock me out" sees the wrong number.
3. **FR-40 and §9.10's "enforced client- and server-side" promise for the never-lock list is only ever half true.** No `CHECK` constraint, trigger, or edge-function validation exists anywhere in `supabase/` for the six never-lock categories, only a plain `jsonb` column. Low practical risk today since stakes never leave the device, but worth either building the check or correcting the docs' claim.
4. **FR-6's "has-stake"/"Stakes active" filter is a two-line TODO that has now outlived its own excuse.** `app/(tabs)/tasks.tsx:366,832` still says it is deliberately deferred because "stakesStore is being rewritten by another workstream." That rewrite (FR-41) is done. This is now pure backlog, not a dependency wait.
5. **FR-17's auto-schedule cutoff setting is still cosmetic.** `store/scheduleStore.ts:207-224`'s `engineRecompute` call still never passes `cutoffDays`, so raising `Settings.autoScheduleCutoffWeeks` in the UI has zero effect on the actual schedule horizon. One-line fix, unfixed for at least two audit rounds now.
